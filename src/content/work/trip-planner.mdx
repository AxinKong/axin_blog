> **Pilot complete — with a caveat.** Four people used this on a real nine-day trip through
> Switzerland. It held up. What is validated is that **the tool works in real conditions** —
> not that strangers would pay for it. The next phase is production, and selling it.

## Context

A nine-day trip through Switzerland for four adults — Zürich → Luzern → Stoos → Interlaken →
Grindelwald → Zermatt — with **scope, timeline, budget and cost** planned and tracked in a
single tool we built for it.

Live: [ralinzain-star.github.io/Switzerland](https://ralinzain-star.github.io/Switzerland/)

## 01. Why not just use an existing planner

We started with the usual options — Notes, Word docs, Notion templates, TripIt, Google Maps
lists, a shared spreadsheet.

All of them handle the same 10% of the problem: what day, what city, what hotel.

None of them covered the rest of what we actually got stuck on:

- What must be done *before* the trip, and by whom
- What transport between each leg, and whether a rail pass pays for itself
- What activity at each stop, and how long it really takes
- How much each person has paid, and how to split the bill proportionally
- How much budget is left, and whether **spent + forecast** will overrun it

**Generic planners go wide.** They cover every destination in the world, and none of them in
any depth. Everything we got stuck on was in the depth — one specific place, one specific
activity, one specific connection.

## 02. The product decisions

Most of what makes this useful is not a feature. It is an all-in-one decision optimizer.

### Must-do before trip

For a working traveller, annual leave, attention, energy and before-trip preparation are the scarce resources. 
The tool organises this by six dimensions: 
visa and certificates, money and payment, mobile sim and applications, forbidden items and alternative items, 
luggage and clothes, notes of reservation-needing places and events

### Hotel and ticket booking states, not a booking list

已訂 / 待訂 / 建議購買 / 比價 as explicit states, with purchase recommendations derived from
the itinerary. Nothing falls through the gap between *"we should book that"* and *"did anyone
book that?"*

### Daily calendar

Every day: where, what activity, at what time — laid out explicitly.

### Map library with every spot marked

Exportable as GeoJSON, so the plan opens in whatever map tool each person already uses.

### Cost and Budget as a live constraint, not a summary

| Phase | What it holds |
| --- | --- |
| Before departure | **Estimated** total per person, flights included |
| [During the trip](https://www.splitwise.com) | **Actual** spend, logged as you go |
| At any moment | Spent + forecast, against the budget |

The point is not only record-keeping. It is being able to answer *"how much has each person
paid, and how do we split this proportionally?"* and *"how much budget is left, and will
spent + forecast overrun it?"* — at any moment, not at the end.

Noted that the team members are from different countries and use different currencies.

TWD / CHF / JPY with a stated conversion line. Prices are quoted in one currency, paid in
another, settled between four people in a third. We used the Splitwise API for the live
settlement rather than rebuilding it — a single-currency tool would have pushed that work
back into a spreadsheet, which is exactly what we were trying to leave behind.

### A retrospective built in

Most planners end when the trip starts. This one has **旅程回顧** — a place to record what
actually happened. We created a cloud folder to let every member upload their photos and videos 
during the trip

That is deliberate: it turns a one-off artefact into an input for the next trip. It is the
feature that makes a *series* of trips better, not just this one.

## 03. What the pilot proved

Four people, nine days, six regions, real bookings, real money.

| | |
| --- | --- |
| Used on the actual trip | Yes |
| Held up in the field | Yes — no fallback to spreadsheets |
| Users | 4 |

**Validated:** the tool works under real conditions everyday — bad signal, changing plans,
split payments, luggage logistics. That is not nothing. Most planning tools are quietly
abandoned on day two in favour of a group chat.

**Not validated:** that anyone outside the pilot group wants this, or would pay for it.

## 04. Phased plan — gated on evidence, not dates

Each phase has an explicit entry condition. If the condition isn't met, the next phase
doesn't start.

| Phase | When | What | Entry condition |
| --- | --- | --- | --- |
| **Idea** | Jun 2026 | **Frame the problem** — existing tools cover 10% of a trip; find what the other 90% is | — |
| **PoC** | Jul 2026 | **Build** — itinerary, pre-trip checklist, booking states, budget model, map | Problem defined and scoped |
| **Pilot** ← *current* | 17–27 Jul 2026 | **Switzerland** — 4 people, 9 days, 6 regions, real bookings, real money | Tool complete enough to depend on in the field |
| **Production** | Late Oct 2026 | **Path B** — one finished plan per destination, sold as a package or a service | Pilot held up in the field without falling back to spreadsheets ✅ |
| **Benefit realization** | Nov 2026 | **Path A** — the skill: inputs → a live planning website | Paying customers on B, and enough hand-built destinations to encode the method |

**Production is unblocked.** Its entry condition was met when the Switzerland trip ended —
what is missing is not evidence, it is a first destination package and a first buyer.

## 05. Next phase — run B first, build toward A

The Switzerland site is not the product. It is **one output**. Two ways to turn it into
something sellable are on the table, and they are genuinely different bets.

### Path A — the planner as a skill

A **skill**: you give it countries, cities, addresses, days and a budget, and it produces the
plan as a live website — itinerary, pre-trip checklist, booking states, budget model, map.

This works because of a split we only noticed after building it by hand — **the answers
change every trip, but the questions don't**:

| | |
| --- | --- |
| **Different every trip** | The itinerary, the rail-pass maths, the local specifics |
| **The same every trip** | What to ask, what to check, and in what order |

### Path B — one finished plan per destination

Build each destination once, sell it as a package or a service. Custom trip planning is already a
paid service in the Chinese-speaking travel market; what it lacks is a tool that makes each
plan reusable instead of hand-built every time.

### The trade-off

| | **A — Skill** | **B — Finished plans** |
| --- | --- | --- |
| What the buyer gets | Inputs → a plan | A finished plan for one place |
| Depth | **Unproven** | Guaranteed — a human researched it |
| Scale | High | One build per destination |
| Time to first revenue | Longer | Shorter |
| Main risk | The method may not transfer | It doesn't scale |

**They are not exclusive. We are going to run B first** — it proves people pay, and each
destination built by hand becomes training material for A. A is where the margin is, if the
method holds.

### Distribution

The plan itself is the marketing asset. A finished itinerary screenshots well — the day
calendar, the map with every spot marked, the budget breakdown — which is exactly what these
platforms reward.

| Channel | What gets posted |
| --- | --- |
| **小红书 (Red)** | Where the Chinese-speaking travel-planning audience already is. Primary channel. |
| **Instagram / Threads** | Visual trip highlights; Threads for the planning story behind them |
| **TikTok** | Short-form — one decision per clip (is the rail pass worth it?) |
| **YouTube** | Long-form walkthrough of a full itinerary and what it cost |
| **X** | Smallest fit for travel, but the cheapest to test |

**【TBD: none of these have been tested. The first job is finding which one converts to a
paying customer, not which one gets views.】**
